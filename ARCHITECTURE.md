# Архитектура — СтройКонтроль

Документ фиксирует ключевые архитектурные решения и их компромиссы. Формат
каждого решения: **Контекст → Решение → Почему не альтернатива → Ограничение.**

---

## 1. Контекст

Вакансия (Mindia KZ) требует senior-уровня по направлениям:

- **Go в production**: API, бизнес-логика, БД, внешние сервисы; обработка
  ошибок, `context`, конкурентное выполнение;
- **React + TypeScript**: интерфейсы, состояние, асинхронность, серверные
  данные, диагностика ошибок UI;
- **PostgreSQL и SQL**: моделирование, транзакции, ограничения, индексы,
  миграции;
- HTTP/REST, **аутентификация и авторизация**, конкурентные изменения,
  повторные запросы, совместимость API;
- Git, Docker;
- unit / интеграционные / **E2E-тесты** против реального бэкенда и БД;
- **AI-функции**: подключение моделей к данным, знаниям и инструментам, права
  доступа и контроль пользователя, проверка качества на реальных задачах;
- работа с AI-агентами (контекст, постановка задач, ревью изменений).

Плюсы (будет плюсом по вакансии): B2B/корпоративные системы, документооборот,
строительная предметная область, ERP, интеграции и миграция данных,
CAD/САПР и BIM, эксплуатация AI-функций, контроль задержек и стоимости.

Демо решает из этого списка максимум и делает предметную область
правдоподобной: управление строительными проектами для строительных и
проектных организаций.

---

## 2. Общая картина

```
        ┌───────────────────────────┐        ┌───────────────────────────────┐
        │  web/ — React 18 + TS      │  HTTP  │  backend/ — Go 1.24            │
        │  Vite, react-router        │ ─────► │  cmd/server → api → service    │
        │  AuthContext / ToastContext│  REST  │            → store → domain     │
        │  услуги API (типизированы) │  JWT   │            → ai (LLM+tools)     │
        └───────────────────────────┘        └───────────────┬───────────────┘
                                                              │
                                             ┌────────────────┴────────────────┐
                                             │  SQLite  |  PostgreSQL           │
                                             │  (один SQL, DB.Rebind)           │
                                             └─────────────────────────────────┘
```

Слои бэкенда строго разделены по направлению зависимостей:
`api → service → store → domain`. Сервисы зависят от **интерфейсов**
(`internal/service/ports.go`), а не от конкретных репозиториев, — это делает
бизнес-логику тестируемой без БД.

---

## 3. Решения

### ADR-001. Двойной драйвер БД под одним SQL (SQLite локально, PostgreSQL в production)

**Контекст.** Вакансия требует PostgreSQL, но локальная машина разработчика
слабая (Docker не тянет), а демо должно запускаться «в один клик».

**Решение.** Один код и один SQL с `?`-плейсхолдерами; `store.DB.Rebind`
преобразует их в `$n` для PostgreSQL и оставляет как есть для SQLite. Два
набора миграций (`migrations/sqlite`, `migrations/postgres`) с идентичной
структурой. Драйвер выбирается `DB_DRIVER`.

**Почему не альтернатива.**
- *Только PostgreSQL* — демо не запустится без Docker/сервера на слабой машине.
- *Только SQLite* — не закрывает обязательное требование вакансии.
- *ORM (GORM/ent)* — скрывает SQL, который вакансия прямо требует; усложняет
  контроль транзакций, ограничений и индексов.

**Ограничение.** Типы колонок в двух миграциях описаны раздельно (`INTEGER`/`REAL`
против `BIGINT`/`DOUBLE PRECISION`); при добавлении таблиц правки нужно вносить
в оба набора. Покрывается интеграционными тестами (опциональный прогон на
PostgreSQL по `TEST_DATABASE_URL`).

### ADR-002. Деньги в минорных единицах, время — в RFC3339Nano (TEXT)

**Контекст.** Финансовые расчёты (бюджет, факт, сметы) не терпят ошибок
округления; формат хранения должен переноситься между СУБД.

**Решение.** Все суммы хранятся как `int64` в минорных единицах (тиын, 1/100 ₸),
в JSON отдаются как `budgetMinor` и т.п. Время — строка RFC3339Nano.
Арифметика — только в целых.

**Почему не альтернатива.** `float`/`numeric` в коде при агрегациях даёт
накопление ошибок; нативная типизация времени по-разному ведёт себя в SQLite
и PostgreSQL.

**Ограничение.** Клиент обязан делить на 100 для отображения (`formatMoney`);
суммы ограничены диапазоном `int64` (для строительных бюджетов заведомо
достаточно).

### ADR-003. Optimistic locking вместо блокировок на уровне БД

**Контекст.** Вакансия отдельно называет «конкурентные изменения» и «повторные
запросы». Два пользователя могут править один объект/смету/документ.

**Решение.** У изменяемых сущностей есть поле `version`. Обновление выполняется
как `UPDATE ... WHERE id = ? AND version = ?`; при нулевом числе строк возвращается
`ErrVersionMismatch` → HTTP **409 `version_mismatch`**. Клиент перезагружает данные.

**Почему не альтернатива.**
- *SELECT FOR UPDATE* на уровне БД — держит транзакцию и соединение на время
  пользовательского размышления, что для веб-формы неприемлемо;
- *last-write-wins* — молчаливая потеря правок одного пользователя другим.

**Ограничение.** Требует, чтобы клиент присылал актуальный `version`; в UI это
инкапсулировано (форма редактирования объекта).

### ADR-004. Матрицы переходов статусов в домене, а не в БД

**Контекст.** Сметы и документы проходят согласование; набор допустимых переходов
и прав должен быть явным и проверяемым.

**Решение.** Легальные переходы описаны в сервисах (сметы:
`draft→on_review→approved|rejected→…`; документы: `draft→submitted→approved|rejected`).
Утверждение/отклонение требует `Role.CanApprove()` (admin|manager) иначе
`ErrForbidden` → 403. Утверждённую смету/документ нельзя удалять и менять
позиции.

**Почему не альтернатива.** Триггеры/CHECK в БД затрудняют сопровождение и
смешивают правила с хранением; статус-машина как generic-фреймворк —
излишняя абстракция для двух сущностей.

**Ограничение.** Правила захарены в коде; при большом числе сущностей потребуется
вынести в таблицу переходов.

### ADR-005. Идентификация и авторизация: JWT (HS256) + роли

**Контекст.** Нужны аутентификация и авторизация, разграничение прав по ролям,
корпоративный B2B-контекст.

**Решение.** Пароли — bcrypt. Вход выдаёт JWT (HS256, issuer `mindia-kz-demo`,
TTL из `JWT_TTL`, по умолчанию 12 часов) с `uid/email/role`. Middleware
проверяет токен и подгружает пользователя (в т.ч. актуальный `is_active`).
Роуты защищены `requireRole(...)`. Роли: admin, manager, estimator, foreman,
customer.

**Почему не альтернатива.**
- *Серверные сессии в памяти* — не переживают перезапуск и не масштабируются
  горизонтально;
- *OAuth/OIDC-провайдер* — избыточно для демо и требует внешней инфраструктуры.

**Ограничение.** HS256 (общий секрет) подходит для одного сервиса; при
нескольких сервисах нужен RS256/ключевой реестр. Нет refresh-токенов —
на демо осознанно (см. «Что осознанно не сделано»).

### ADR-006. AI-ассистент как ограниченный инструментами агент внутри продукта

**Контекст.** Вакансия требует «соединять модели с данными, знаниями и
инструментами, уважать права доступа и контроль пользователя; проверять
качество». Пользователь отдельно потребовал: ассистент — **только помощник
внутри платформы**, а не универсальный ИИ; лимит ~500 000 токенов
(вход+выход), после исчерпания — «демо-режим закончился».

**Решение.**
- LLM-клиент с OpenAI-совместимым `/chat/completions`.
- **Tool-calling** с жёстким белым списком инструментов (`internal/ai/tools.go`):
  `list_projects`, `project_overview`, `analyze_estimate`,
  `list_pending_approvals`, `search_normative`, `list_documents`. Каждый
  инструмент работает под правами вызывающего пользователя.
- **RAG по нормативной базе**: `search_normative` ищет по СН РК/СП РК/ГОСТ/СТ РК,
  найденные коды возвращаются как источники ответа.
- **Системный промпт**, ограничивающий ассистента продуктом; на офтопик он
  отказывает.
- **Бюджет токенов**: сумма входных и выходных токенов хранится в таблице
  `ai_usage` (scope `global`); при достижении лимита ассистент отвечает
  фиксированным сообщением «Демо-режим ассистента закончился…» и не вызывает
  модель.
- Ограничение числа шагов tool-calling на один запрос (`AI_MAX_TOOL_CALLS`).
- **Офлайн-fallback**: без `AI_API_KEY`/`AI_BASE_URL` ассистент отвечает
  детерминированно (по ключевым словам выбирает тот же инструмент и
  формирует ответ), поэтому демо работает без внешнего провайдера.

**Почему не альтернатива.**
- *Свободный чат-бот* — прямо запрещено требованием (не универсальный ИИ);
- * Только промпт без инструментов* — модель выдумывала бы числа вместо чтения
  реальных данных;
- *Векторная БД для RAG* — избыточна на 8 нормативных документах; выбран
  лексический ранкинг по совпадению токенов и кода документа.

**Ограничение.** Лимит токенов — общий на инстанс (`scope='global'`), а не
персональный; офлайн-режим даёт шаблонные ответы, а не полноценный диалог.

### ADR-007. Транзакции там, где меняется несколько таблиц

**Контекст.** Создание сметы с позициями и пересчёт итога должны быть атомарны.

**Решение.** `EstimateRepo.Create` вставляет смету и позиции в одной транзакции;
`RecomputeTotal` считает сумму по позициям в БД (`SUM`). Утверждение КС-2/КС-3
через `DocumentService` вызывает `ProjectRepo.AddSpent`, увеличивая фактические
затраты объекта.

**Почему не альтернатива.** Раздельные вставки без транзакции оставляют
«осиротевшие» сметы без позиций при сбое на середине.

**Ограничение.** Списочные выборки не оборачиваются в транзакции (только чтение);
вложенные транзакции не поддерживаются (одна на операцию).

### ADR-008. Ограничения и индексы в схеме БД

**Контекст.** Вакансия явно перечисляет constraints и indexes как требование.

**Решение.** CHECK на статусы и неотрицательность сумм/процентов; UNIQUE
(`users.email`, `projects.code`, `estimates(project_id,number)`,
`documents(project_id,number)`); внешние ключи с политиками
`ON DELETE CASCADE/SET NULL`; индексы под реальные запросы (статусы, менеджер,
создатель, проект/тип документа, `activity(entity_type,entity_id)`,
`ai_conversations(user_id,updated_at DESC)`).

**Почему не альтернатива.** Ограничения в приложении пропускают «грязные» данные
из скриптов/ручных правок; индексы без привязки к запросам бесполезны.

**Ограничение.** Набор индексов минимален под текущие выборки; при росте данных
потребуется ревизия по `EXPLAIN ANALYZE`.

### ADR-009. Единый маппинг ошибок домена в HTTP

**Контекст.** Нужны предсказуемые коды ответов и машиночитаемые ошибки.

**Решение.** Типизированные ошибки домена (`ErrNotFound`, `ErrConflict`,
`ErrValidation`, `ErrForbidden`, `ErrUnauthorized`, `ErrPreconditionFailed`,
`ErrVersionMismatch`) централизованно маппятся в `api.writeError`:
422 (с полем), 404, 409/`version_mismatch`, 412, 401, 403, 500. Тело ошибки:
`{ error, message, field? }`.

**Почему не альтернатива.** Разрозненные `http.Error` в хендлерах дают
несогласованные коды и тексты; клиенту пришлось бы разбирать строки.

**Ограничение.** Сообщения валидации приходят по одному полю за раз (не
накапливаются в список).

### ADR-010. DTO/граница API: домен не отдаётся «как есть»

**Контекст.** Нельзя вернуть клиенту `PasswordHash` и служебные поля.

**Решение.** У доменных структур JSON-теги и `json:"-"` для чувствительных полей
(`User.PasswordHash`, `NormativeDoc.Keywords`); список — в конверте
`{ items, total, limit, offset }`; деньги — минорные единицы; опциональные поля
`omitempty`.

**Почему не альтернатива.** Отдельный слой DTO для каждого ответа в демо
избыточен; тег `json:"-"` даёт тот же эффект при меньшем числе файлов.

**Ограничение.** При усложнении контрактов (версии API) потребуются явные DTO и
стратегия совместимости (см. «Что осознанно не сделано»).

### ADR-011. Конфигурация только через окружение, с безопасными дефолтами

**Контекст.** Демо должно запускаться без подготовки, но production не должен
стартовать с небезопасными значениями.

**Решение.** `config.Load` читает переменные окружения; в production отсутствие
`JWT_SECRET` — фатальная ошибка при старте; в development допускается
небезопасный дефолт. AI автоматически отключается, если нет ключа или базового URL.

**Почему не альтернатива.** Хардкод секретов или конфиг-файл с ключами в
репозитории — уязвимость; отсутствие дефолтов ломает первый запуск.

**Ограничение.** Нет поддержки `.env`-файлов «из коробки» (полагаемся на
окружение/`docker compose`); пример — `backend/.env.example`.

### ADR-012. Graceful shutdown и таймауты HTTP

**Контекст.** Production-сервис должен корректно завершаться и не «висеть».

**Решение.** `http.Server` с `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`
(90 с — с запасом на AI-запросы), `IdleTimeout`; перехват SIGINT/SIGTERM и
`Shutdown` с таймаутом 15 с; middleware `Timeout(60s)` на запрос.

**Почему не альтернатива.** Мгновенный выход обрывает активные запросы; сервер
без таймаутов уязвим к медленным клиентам.

**Ограничение.** Значения захардены разумными константами, не вынесены в конфиг.

### ADR-013. Детерминированная AI-проверка смет отдельно от LLM

**Контекст.** «Проверка качества на реальных задачах» и контроль стоимости:
тяжёлую аналитику нельзя поручать модели (дорого, невоспроизводимо).

**Решение.** Аномалии смет вычисляются детерминированно (`EstimateService.Analyze`):
дубли позиций, неположительные цены/объёмы, арифметические расхождения
(`total ≠ qty × price`), аномальная доля одной позиции (> 40 % при > 3 позициях).
Возвращаются риск-скор 0–100 и список замечаний. LLM-ассистент может вызвать
эту проверку инструментом `analyze_estimate`, но не подменяет её.

**Почему не альтернатива.** «Пусть модель найдёт ошибки в смете» — медленно,
дорого и не даёт гарантированно одинакового результата; инженерная проверка
должна быть проверяемой.

**Ограничение.** Набор правил ограничен и не заменяет нормативную экспертизу.

## 4. Производительность

- Индексы под фактические выборки; списочные ответы пагинируются
  (`limit` по умолчанию 20, максимум 100).
- Подсчёт количества позиций сметы — подзапросом, без N+1 на клиенте.
- Дашборд собирает сводку агрегатными запросами (`Summary`), а не серией
  отдельных обращений.
- SQLite открывается в режиме WAL с `busy_timeout`; `MaxOpenConns=1` исключает
  конкуренцию за файл. Для PostgreSQL пул — 10 соединений.
- Фронтенд: прод-сборка ~229 КБ JS (gzip ~70 КБ), код-сплит по маршрутам
  не делался (приложение небольшое).

**Что не измерялось.** Нагрузочное тестирование и профилирование не проводились;
приведённые числа — статические (размер сборки) и архитектурные (индексы,
отсутствие N+1), а не результаты бенчмарков.

---

## 5. Надёжность

- Валидация входных данных на границе API (типы, диапазоны, даты, неотрицательные
  суммы) → 422 с указанием поля.
- Optimistic locking на конкурентные правки → 409 `version_mismatch`.
- Транзакции на многотабличные операции.
- Идемпотентность: повторный `Seed` и повторный `Migrate` не создают дублей.
- AI-запросы: таймаут, ограничение числа tool-call шагов, лимит токенов,
  офлайн-fallback при недоступности провайдера/отсутствии ключа.
- Graceful shutdown; `GET /healthz` для healthcheck в Docker.

---

## 6. Что осознанно не сделано

- **Refresh-токены, отзыв сессий, rate limiting** — для демо достаточно TTL и
  простого входа; в production это обязательный минимум.
- **RS256 и внешний Identity Provider (OIDC/OAuth)** — HS256 проще для одного
  сервиса.
- **Полноценная RAG с векторным индексом и эмбеддингами** — на 8 нормативных
  документах лексический поиск достаточен; векторная БД усложнила бы запуск.
- **Версионирование API (`/v2`) и формальная политика совместимости** —
  контракт стабилен, но версии пока не вводятся.
- **BIM/CAD и импорт IFC, интеграции с ERP, миграция данных** — упомянуты в
  вакансии как плюсы; вне объёма демо.
- **Python** — не используется (в вакансии — плюс, основной стек Go).
- **CI/CD-пайплайны** — Docker и compose есть; конвейеры GitHub Actions не
  настроены.
- **Векторная БД, кэш (Redis), очереди** — при текущем объёме не нужны.

## 7. Что проверено, а что нет

**Проверено (реальный запуск):**

- `go build ./...`, `go vet ./...` — успешно;
- запуск сервера и сквозной прогон API (вход по ролям, дашборд, объекты, сметы,
  анализ аномалий, документы, нормативы, AI-usage, RBAC → 403, валидация → 422);
- `npm run typecheck`, `npm test`, `npm run build` — успешно.

**Не проверено в среде разработчика:**

- работа с PostgreSQL (нет локального Docker/сервера) — SQL и миграции
  рассчитаны на него, но прогон на реальном PostgreSQL не выполнялся;
- работа с реальным LLM-провайдером (нет ключа в среде) — проверен офлайн-режим
  и структура вызовов;
- браузерная визуальная проверка интерфейса (см. README) — не выполнялась в
  среде сборки.
